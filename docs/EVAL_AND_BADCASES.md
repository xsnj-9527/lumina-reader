# Lumina Reader 检索评测与 Badcase 拆解记录

本文档记录 Lumina Reader 在**零外部向量库本地检索**、**PDF 划词噪声清洗**与**Prompt 场景分流**三个核心环节的可复现评测方法、量化对比数据与典型 Badcase 优化过程。

所有结论均由仓库内置脚本 [`scripts/eval-retrieval.mjs`](../scripts/eval-retrieval.mjs) 直接导入真实源码（`docContextIndex.ts`、`textCleaner.ts`、`prompts.ts`）实测生成，零额外依赖，执行以下命令即可复现：

```bash
npm test
# 或
npm run eval
```

## 1. 本地检索对比评测（Suite A · 20 组多章节问答）

### 评测设计
构造 14 章节 + 9 篇工程附录的中英文混合技术文档（**8,855 字符 / 24 分块**），在统一上下文预算上限 **2,800 字符**下，设计两类真实阅读提问：
- **跨章节检索（14 条）**：读者处于文档开头或末尾时，追问遥远章节的具体实现细节与参数。
- **局部视窗指代问答（6 条）**：读者针对当前屏幕段落发出的泛指提问（如「这里作者为什么改用新实现？」「当前这段提到的几个痛点是什么？」），提问本身不包含原章节专有名词。

### 实测对比结果

| 检索策略 | 总命中率（20 条） | 局部指代命中（6 条） | 跨章检索命中（14 条） | 特点与短板 |
| :--- | :---: | :---: | :---: | :--- |
| 无索引头部截断 | 8 / 20（40.0%） | — | — | 仅能覆盖开篇内容，中后段问答完全盲区 |
| 纯 BM25 全文检索 | 16 / 20（80.0%） | **2 / 6** | 14 / 14 | 精确关键词召回强，但对「这里/当前这段」类指代提问大量失分 |
| **当前视窗 + BM25 混合（Lumina）** | **20 / 20（100.0%）** | **6 / 6** | **14 / 14** | 兼顾当前阅读现场与全书远距离关联，无重复拼接 |

### 上下文控本与超长文档导读抽样
- **单次伴读控本**：平均输入上下文 **2,590 字符**，相比全文输入节省 **70.8%** 上下文开销，且严格不突破 `maxChars` 硬上限。
- **超长文档全文导读**：对 **34,876 字符**超长文档自动启用「完整 TOC + 开头导言 + 中间均匀抽样 + 结语收束」，压缩至 **13,932 字符**（严格 ≤ 15,000 字符），避免超长上下文引发中间遗忘（Lost in the Middle）。

## 2. 边界回归测试（Suite B & Suite C · 14 组断言）

- **Suite B（PDF / 流式文本划词清洗，8 / 8 PASS）**：验证英文小写跨行连字符合并、大写复合专有名词保留连字符、中文硬换行拼接、PDF 汉字间孤立空格清洗（且非 PDF 模式不误伤）、软连字符 `U+00AD` / 零宽空白符清除、真实双换行段落保留。
- **Suite C（划词模式分流与 Prompt 约束，6 / 6 PASS）**：验证 1–3 词英文术语准确进入 `word` 语境词典模式、长句/含标点/多行/中文文本进入 `sentence` 原位译文模式，以及两套系统提示词均严格携带格式与「禁止开场白」输出约束。

## 3. 典型 Badcase 拆解与迭代记录

### Badcase 1：双栏 PDF 划词出现断词与中文碎空格导致误译
- **现象**：从学术 PDF 文本层划选 `compre-\nhension` 或 `注 意 力 机 制` 直接送模型，词典模式将其当成非法词元，译文出现断句错乱。
- **根因**：PDF 文本层按视觉行切分且字符间距常被 `pdfjs` 解析为空格；行尾连字符既可能是排版断词，也可能是专有名词连接符（如 `GPT-\n4o`）。
- **方案（`src/utils/textCleaner.ts`）**：按后续字母大小写区分策略——小写字母续接直接合并断词，大写字母或数字续接保留连字符仅去换行；仅在 `isPdf=true` 时合并连续汉字间孤立单空格，同时用占位符保护真实空行段落。

### Badcase 2：伴读提问使用代词（「这段」「这里」）时纯关键词检索失效
- **现象**：读者在阅读第 7 章时问「这部分提到的取舍逻辑怎么理解」，纯 BM25 因为问题不含章节专有名词，召回了无关段落，模型只能胡乱猜测或答非所问。
- **根因**：阅读伴读与通用搜索的本质差异在于存在强隐式状态——**用户当前的视觉焦点本身就是核心上下文**。
- **方案（`src/utils/docContextIndex.ts`）**：优先以当前页码或滚动进度比例定位锚点块，向两侧扩展约 1,500 字符（上限占预算 42%）作为「当前阅读位置附近内容」，再将视窗块加入 `excludeIds` 后在剩余全书执行 BM25 Top 4 检索，在评测集上将局部指代命中率由 **2/6 提升至 6/6**。

### Badcase 3：划词翻译卡片输出冗长开场白，破坏专注阅读体验
- **现象**：用户划选一个英文术语或长句，通用翻译 Prompt 经常输出「好的，这句话结合上下文的意思是……」，导致指尖小浮层被撑爆且视觉割裂。
- **根因**：单词/短术语与整句的阅读诉求不同，且未在 Prompt 层面约束输出边界与格式骨架。
- **方案（`src/services/prompts.ts`）**：在前端用零延迟规则函数 `detectSelectionMode` 自动分流——1–3 个英文词元且无句末标点、长度 ≤ 36 字符走 3 行紧凑 Markdown「语境词典」；其余走「原位译文」并明令禁止开场白、引号与前缀，同时隐式附带选区前后各 360 字符语境但不回显到卡片。

### Badcase 4：推理模型混合思考导致指尖划词首字延迟（TTFT）过高
- **现象**：使用带思考链的模型处理划词翻译时，模型先输出数百字思考过程才吐出第一句译文，等待感极强。
- **根因**：伴读深聊需要强推理，但划词翻译是高频低延迟微交互，单一模型配置无法兼顾两类场景。
- **方案（`src/services/aiService.ts` + `SettingsModal.tsx`）**：引入多模型档案库（内置小米 MiMo、Gemini、DeepSeek 等预设），支持为「伴读答疑」与「划词翻译」独立路由模型，并在划词场景提供「关闭混合思考模式」开关以显著降低首字延迟。
